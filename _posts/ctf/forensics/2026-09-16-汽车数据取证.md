## 场景背景

某品牌智能网联汽车（车型：EV-X2024）发生疑似远程入侵事件，车主反映车辆在无人操作情况下自动解锁、导航被篡改、行车记录仪视频文件丢失。执法机构依法对该车辆车机系统进行完整镜像提取，镜像文件为 `EVX2024_HU_full.img`（大小约 32GB，基于 Android Automotive 系统），并已通过哈希校验（SHA-256）。请基于该镜像完成以下取证分析任务。

## 第1题：镜像完整性验证与挂载

**题目：**
取证人员拿到车机系统镜像文件 `EVX2024_HU_full.img` 后，需要首先验证镜像完整性，并将镜像以只读方式挂载以便后续分析。请描述完整操作流程。

**解题步骤：**

**第一步：校验镜像哈希值**
```bash
# 计算镜像 SHA-256 值，与移交清单中的原始哈希比对
sha256sum EVX2024_HU_full.img
# 同时计算 MD5 作为辅助验证
md5sum EVX2024_HU_full.img
```
将输出结果与案件移交文件中记录的原始哈希值逐字符核对，确保两者完全一致，方可进入下一步。若不一致，镜像可能已被篡改，须记录差异并上报。

**第二步：查看镜像分区结构**
```bash
# 查看分区表，识别各分区偏移量和大小
fdisk -l EVX2024_HU_full.img
# 或使用 mmls（The Sleuth Kit）
mmls EVX2024_HU_full.img
```
记录每个分区的起始扇区（Start）、结束扇区（End）及文件系统类型。

**第三步：只读挂载目标分区**
```bash
# 以 userdata 分区为例，假设起始扇区为 2097152，扇区大小 512 字节
# 偏移量 = 起始扇区 × 512
sudo mount -o ro,loop,offset=$((2097152*512)) EVX2024_HU_full.img /mnt/evx_userdata
```
`ro` 参数确保只读挂载，保护原始证据不被修改。

**第四步：记录挂载信息并固定证据状态**
```bash
# 记录挂载时间、操作人员、哈希值到取证日志
echo "挂载时间: $(date)" >> forensic_log.txt
echo "操作人员: XXX" >> forensic_log.txt
echo "SHA256: $(sha256sum EVX2024_HU_full.img)" >> forensic_log.txt
```

**答题要点：** 镜像完整性验证是取证第一原则，挂载必须使用只读模式，所有操作须留痕记录。

## 第2题：提取车机系统基本信息

**题目：**
从镜像中提取车机系统版本、设备标识符（VIN绑定信息）、已安装应用列表等基础信息，用于确认分析对象的同一性。

**解题步骤：**

**第一步：查找系统版本信息**
```bash
# Android Automotive 系统版本信息存储在 system 分区
# 挂载 system 分区后查找 build.prop
cat /mnt/evx_system/system/build.prop | grep -E "ro.build|ro.product|ro.version"
```
重点关注字段：`ro.build.version.release`（系统版本）、`ro.product.model`（车型）、`ro.build.fingerprint`（构建指纹）。

**第二步：提取设备唯一标识符**

```bash
# Android ID 和设备序列号
cat /mnt/evx_system/system/build.prop | grep "ro.serialno"
# VIN 绑定文件通常在车厂定制目录
find /mnt/evx_userdata -name "*.conf" | xargs grep -l "VIN" 2>/dev/null
find /mnt/evx_userdata -path "*/vehicle/*" -name "*.xml" 2>/dev/null
# 车辆识别号
搜vin，在persist.sys.vin文件
```

**第三步：获取已安装应用列表**
```bash
# 系统预装应用
ls /mnt/evx_system/system/app/
ls /mnt/evx_system/system/priv-app/
# 用户安装应用（data 分区）
ls /mnt/evx_userdata/data/app/
# 导出应用列表
ls /mnt/evx_userdata/data/app/ > installed_apps.txt
```

**第四步：整理信息填写取证记录表**
将系统版本、VIN、序列号、应用列表等统一记录到《数字证据检验报告》的"检材基本信息"栏目。

**答题要点：** 系统同一性验证是后续所有分析的前提，VIN与车辆档案比对可确认镜像来源车辆。

## 第3题：定位非法远程访问日志

**题目：**
车主反映某天凌晨3点车辆自动解锁，怀疑遭到远程入侵。请从镜像中找出系统日志，定位异常远程访问记录。

**解题步骤：**

**第一步：定位 Android 系统日志目录**

```bash
# Android 日志通常存储在以下位置
ls /mnt/evx_userdata/system/tombstones/   # 崩溃日志
ls /mnt/evx_userdata/misc/logd/           # 主系统日志
ls /mnt/evx_userdata/data/log/            # 应用日志
# 查找所有 .log 文件
find /mnt/evx_userdata -name "*.log" -type f 2>/dev/null
```

**第二步：提取并过滤远程访问相关日志**
```bash
# 复制日志文件到工作目录（不修改原始挂载点）
cp -r /mnt/evx_userdata/misc/logd/ ./logs_backup/
# 搜索解锁相关关键词
grep -r -i "unlock\|remote\|ota\|ssh\|adb\|connect" ./logs_backup/ | grep "03:0[0-9]"
# 按时间段过滤（假设事发日期为2024-03-15）
grep "2024-03-15 03:" ./logs_backup/main.log
```

**第三步：分析 ADB/网络连接日志**
```bash
# 查找 ADB 连接记录
grep -r "adb\|adbd" ./logs_backup/
# 查找网络连接日志
find /mnt/evx_userdata -name "netd*" -o -name "connectivity*" | xargs grep -l "CONNECT" 2>/dev/null
# 查看 WiFi 连接历史
cat /mnt/evx_userdata/misc/wifi/WifiConfigStore.xml
```

**第四步：提取关键时间线**
将发现的异常日志条目按时间顺序整理，构建攻击时间线，记录首次异常连接IP、端口、操作行为等。

**答题要点：** 重点关注案发时间窗口内的 ADB 连接、OTA 下载、解锁指令日志；注意日志时间与车辆时区的对应关系。

## 第4题：分析被篡改的导航数据

**题目：**
车主反映其常用导航目的地（家庭地址）被修改为陌生地址，请从镜像中找到导航应用的数据库，提取历史目的地记录，并判断是否存在篡改痕迹。

**解题步骤：**

**第一步：定位导航应用数据目录**
```bash
# 查找导航相关应用包名
ls /mnt/evx_userdata/data/data/ | grep -i "navi\|map\|gaode\|baidu\|tencent"
# 假设包名为 com.ev.navigation，进入其数据目录
ls /mnt/evx_userdata/data/data/com.ev.navigation/
ls /mnt/evx_userdata/data/data/com.ev.navigation/databases/
```

**第二步：提取并解析 SQLite 数据库**
```bash
# 复制数据库文件到工作目录
cp /mnt/evx_userdata/data/data/com.ev.navigation/databases/navigation.db ./
# 使用 sqlite3 查看表结构
sqlite3 navigation.db ".tables"
sqlite3 navigation.db ".schema favorite_places"
# 查询历史目的地
sqlite3 navigation.db "SELECT * FROM favorite_places ORDER BY modify_time DESC;"
sqlite3 navigation.db "SELECT * FROM history_destinations ORDER BY timestamp DESC LIMIT 50;"
```

**第三步：检查记录的修改时间异常**
```bash
# 重点查看修改时间与正常使用时间是否吻合
sqlite3 navigation.db "SELECT name, address, latitude, longitude, create_time, modify_time FROM favorite_places WHERE name='家' OR name='home';"
# 对比文件系统层面的时间戳
stat /mnt/evx_userdata/data/data/com.ev.navigation/databases/navigation.db
```

**第四步：还原被修改的内容**
结合 SQLite WAL（Write-Ahead Log）文件分析历史修改记录：
```bash
# 检查 WAL 文件
ls -la ./navigation.db-wal ./navigation.db-shm
# 使用取证工具（如 DB Browser for SQLite 或 Autopsy）分析已删除/修改记录
```

**答题要点：** 重点比对"家"等常用地址的 `modify_time` 与案发时间；WAL 文件可能保留修改前的原始数据。

## 第5题：恢复被删除的行车记录仪视频文件

**题目：**
车主反映案发时间段的行车记录仪视频文件已不存在，请从镜像的存储分区中尝试恢复被删除的视频文件。

**解题步骤：**

**第一步：定位行车记录仪存储分区**
```bash
# 车机通常将行车记录仪数据存储在独立分区或 SD 卡镜像中
# 查看分区列表，寻找 dashcam、dvr、media 相关分区
mmls EVX2024_HU_full.img
# 挂载疑似分区
sudo mount -o ro,loop,offset=$((SECTOR*512)) EVX2024_HU_full.img /mnt/evx_dashcam
ls /mnt/evx_dashcam/
```

**第二步：使用 Autopsy 或 PhotoRec 恢复删除文件**
```bash
# 方法一：使用 PhotoRec（命令行）
photorec /d ./recovered/ EVX2024_HU_full.img
# 恢复后按文件类型分类，选择 mp4/avi/ts 等视频格式

# 方法二：使用 foremost 按文件头特征恢复
foremost -t mp4,avi -i EVX2024_HU_full.img -o ./foremost_output/
```

**第三步：验证恢复文件的时间戳**
```bash
# 查看恢复视频的元数据
ffprobe recovered_video.mp4 2>&1 | grep -E "Duration|creation_time|encoder"

exiftool recovered_video.mp4 | grep -i "time\|date"
```

**第四步：筛选案发时间段文件**
将所有恢复的视频文件按录制时间排序，筛选出案发时间窗口内的视频，核实视频画面与案件事实的对应关系，并计算恢复文件的 MD5 作为证据固定。

**答题要点：** 文件删除后在分区中往往仅清除目录项，数据块仍存在，PhotoRec 通过文件头签名可有效恢复；恢复后必须固定哈希。

## 第6题：分析恶意应用安装痕迹

**题目：**
怀疑攻击者通过某恶意 APK 植入后门程序，请从镜像中查找非官方渠道安装的应用，分析其权限申请情况及可疑行为。

**解题步骤：**

**第一步：列举所有用户安装的 APK**
```bash
# data/app 目录存放用户安装的应用
ls /mnt/evx_userdata/data/app/
# 对比系统预装白名单（从 system/app 获取）
ls /mnt/evx_system/system/app/ > system_apps.txt
ls /mnt/evx_userdata/data/app/ > user_apps.txt
# 找出非系统自带的应用
diff system_apps.txt user_apps.txt
```

**第二步：提取并分析可疑 APK**
```bash
# 找到可疑 APK 文件
find /mnt/evx_userdata/data/app/ -name "*.apk" | xargs -I{} cp {} ./apk_analysis/
# 计算哈希，上传 VirusTotal 查询（线下分析时使用 apktool）
md5sum ./apk_analysis/*.apk
apktool d suspicious.apk -o ./decompiled/
```

**第三步：分析 AndroidManifest.xml 权限声明**
```bash
# 查看权限申请
cat ./decompiled/AndroidManifest.xml | grep -i "uses-permission"
# 重点关注危险权限
grep -E "RECORD_AUDIO|CAMERA|ACCESS_FINE_LOCATION|READ_CONTACTS|SEND_SMS|INTERNET|RECEIVE_BOOT_COMPLETED" ./decompiled/AndroidManifest.xml
```

**第四步：检查应用安装时间与来源**
```bash
# 查看 packages.xml 中的安装信息
grep -A 5 "com.suspicious.app" /mnt/evx_userdata/system/packages.xml
# 重点字段：installTime（安装时间）、installer（安装来源）、codePath（安装路径）
```

**答题要点：** `installer` 字段为 `null` 或非官方应用商店时高度可疑；`RECEIVE_BOOT_COMPLETED` + `INTERNET` 权限组合是后门的典型特征。

## 第7题：提取车辆 CAN 总线通信日志

**题目：**
车机系统中记录了部分 CAN 总线通信数据，请找到相关日志文件，解析其中的车门解锁指令，确认非法解锁操作的来源。

**解题步骤：**

**第一步：定位 CAN 总线日志存储位置**
```bash
# 车厂通常将 CAN 日志存储在专用目录
find /mnt/evx_userdata -name "*.can" -o -name "can_log*" -o -name "vehicle_log*" 2>/dev/null
find /mnt/evx_userdata -path "*/vehicle/*" -name "*.bin" 2>/dev/null
find /mnt/evx_userdata -path "*/diagnostics/*" 2>/dev/null
```

**第二步：解析 CAN 数据格式**
```bash
# 若为标准 .asc 格式（Vector CANalyzer 导出格式）
head -50 vehicle_log.asc
# 使用 cantools 或 python-can 解析
pip install cantools python-can
python3 -c "
import cantools
db = cantools.database.load_file('vehicle.dbc')  # 需要对应车型的 DBC 文件
# 解析门控制报文（通常 CAN ID: 0x3B3 或厂商定义）
print(db.get_message_by_name('DoorControl'))
"
```

**第三步：筛选解锁指令报文**
```bash
# 按时间过滤案发时间段的 CAN 报文
grep "2024-03-15 03:" vehicle_log.asc
# 搜索门控制相关 CAN ID（需参考车型 DBC 文件）
grep "0x3B3\|0x3BA" vehicle_log.asc | grep -E "03:0[0-5]"
```

**第四步：关联日志确认指令来源**
将 CAN 解锁指令的时间戳与系统日志中的远程连接时间戳进行关联比对，若两者时间吻合（误差 <1秒），则可证明远程连接触发了解锁指令。整理关联证据写入分析报告。

**答题要点：** CAN 报文解析需要对应车型的 DBC 文件；时间戳关联分析是证明"远程操控导致解锁"的核心证据链。

## 第8题：分析 OTA 更新记录中的异常包

**题目：**
怀疑攻击者通过伪造 OTA 更新包植入恶意代码，请从镜像中提取 OTA 更新历史记录，分析是否存在未经官方签名的更新包。

**解题步骤：**

**第一步：查找 OTA 更新记录文件**
```bash
# Android OTA 记录通常在以下位置
find /mnt/evx_userdata -name "recovery-from-boot.p" 2>/dev/null
find /mnt/evx_userdata -name "*.zip" -path "*/ota/*" 2>/dev/null
cat /mnt/evx_system/system/build.prop | grep "ro.build.version.incremental"
# 查看 OTA 安装历史日志
find /mnt/evx_userdata -name "last_install" -o -name "recovery_log*" 2>/dev/null
```

**第二步：提取 OTA 包并验证签名**
```bash
# 复制 OTA 包到工作目录
cp /path/to/ota_package.zip ./ota_analysis/
# 解压查看签名文件
unzip -l ota_package.zip | grep "META-INF"
unzip ota_package.zip META-INF/CERT.SF META-INF/CERT.RSA -d ./ota_sig/
# 查看证书信息
openssl pkcs7 -inform DER -in ./ota_sig/META-INF/CERT.RSA -noout -print_certs -text | grep -E "Issuer|Subject|Validity"
```

**第三步：与官方证书比对**
```bash
# 提取官方系统签名证书（从已知正版镜像）
keytool -printcert -file ./ota_sig/META-INF/CERT.RSA
# 比对证书指纹（SHA-1 Fingerprint）
# 若与官方证书指纹不同，则该 OTA 包非官方发布
```

**第四步：分析 OTA 包内容**
```bash
# 解压 OTA 包分析修改内容
unzip ota_package.zip -d ./ota_content/
# 查看 system 分区修改了哪些文件
ls ./ota_content/system/
# 重点检查 /system/bin/ 中是否有新增可执行文件
```

**答题要点：** 合法 OTA 包必须携带厂商私钥签名；证书 Issuer 与 Subject 相同（自签名）或与官方不符时为高危特征。

## 第9题：提取蓝牙配对历史与设备指纹

**题目：**
攻击者可能通过蓝牙漏洞（如 BlueBorne）近距离入侵车机，请从镜像中提取蓝牙配对历史记录，获取曾连接过的外部设备信息。

**解题步骤：**

**第一步：定位蓝牙配置文件目录**
```bash
# Android 蓝牙配对信息存储位置
ls /mnt/evx_userdata/misc/bluedroid/
# 主要文件：bt_config.conf（配对设备列表）
cat /mnt/evx_userdata/misc/bluedroid/bt_config.conf
```

**第二步：解析蓝牙设备记录**
```bash
# bt_config.conf 为 INI 格式，每个 [MAC地址] 段对应一个设备
# 提取所有配对设备的 MAC 地址和名称
grep -E "^\[|Name|DevClass|Timestamp" /mnt/evx_userdata/misc/bluedroid/bt_config.conf
# 格式示例：
# [AA:BB:CC:DD:EE:FF]
# Name = iPhone_of_Attacker
# Timestamp = 1710432000
```

**第三步：还原设备连接时间**
```bash
# 将 Unix 时间戳转换为可读时间
python3 -c "import datetime; print(datetime.datetime.fromtimestamp(1710432000))"
# 筛选案发时间前后配对的设备
awk '/^\[/{mac=$0} /Timestamp/{print mac, $0}' bt_config.conf | sort -k3
```

**第四步：MAC 地址厂商查询**
将提取的 MAC 地址前三字节（OUI）提交至 IEEE OUI 数据库（https://regauth.standards.ieee.org）查询设备制造商，结合设备名称和时间戳，判断是否存在可疑外部设备接入，并将 MAC 地址作为线索移交侦查部门。

**答题要点：** MAC 地址的 OUI 部分可识别设备品牌；`Timestamp` 字段记录最后一次连接时间，与案发时间的吻合度是关键证据。

## 第10题：撰写车机取证综合分析报告

**题目：**
综合前9题的分析结果，按照电子数据鉴定规范撰写《车机系统数字证据检验报告》，说明报告的必备要素和证据链完整性要求。

**解题步骤：**

**第一步：整理证据清单**
```
证据清单应包含：
- 检材名称：车机系统完整镜像（EVX2024_HU_full.img）
- 检材来源：×× 公安机关，案件编号 ××
- 提取时间：YYYY-MM-DD HH:MM:SS
- 提取方式：硬件写保护 + dd 克隆
- 原始哈希（SHA-256）：×××（由移交方提供）
- 检验哈希（SHA-256）：×××（本次计算）
- 哈希一致性：一致 ✓
```

**第二步：构建攻击时间线**
按时间顺序整理各题发现的证据节点：
```
03:02:15 - 检测到来自 IP 192.168.4.x 的 ADB 连接（第3题）
03:02:18 - 恶意 APK "SystemService.apk" 被静默安装（第6题）
03:02:45 - CAN 总线收到门解锁指令 0x3B3（第7题）
03:03:00 - 导航"家"地址被修改（第4题）
03:05:30 - 行车记录仪视频文件被删除（第5题）
```

**第三步：撰写检验结论**
```
结论要素：
1. 检材同一性：镜像哈希与原始哈希一致，检材未被篡改
2. 入侵确认：在系统日志中发现非授权远程 ADB 连接
```
